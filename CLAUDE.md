# EASY TRAV — Authoritative Development Instructions

This file is the permanent, authoritative development specification for this repository.
It overrides default assistant behaviour, generic Next.js habits, and any conventions
carried in from other projects. Read it in full before writing code. Keep it updated as
the project's locked decisions evolve — do not delete or weaken a rule here without the
repository owner's explicit instruction.

`@AGENTS.md` above is imported deliberately: `next dev` regenerates `AGENTS.md` with
version-specific Next.js rules. Keep that import at the top of this file.

---

## 1. Project identity

**Easy Trav** is a standalone travel product with its own complete visual identity and
its own reference system. It is not a derivative of any other project.

### 1.1 Hard isolation rule

This repository is for Easy Trav **only**.

**Never** import, port, copy, adapt, translate, or take inspiration from the Hathor
Booking System (or any other unrelated repository present on this machine or in an
adjacent working directory). This prohibition covers, without exception:

- styling, CSS files, CSS variables, design tokens
- components, hooks, layout structures, page compositions
- branding, names, copy, logos, imagery, assets
- colour palettes, typography, font pairings
- animation choreography, scroll signatures, motion systems
- "design DNA", editorial systems, or any project-specific design skill

If a Hathor skill, file, or instruction is loaded into context while working in this
repository, **ignore it**. Being able to read those files is not permission to use them.
If a request appears to ask for Hathor material here, stop and ask the owner first.

Easy Trav's visual identity, design tokens, and reference imagery are supplied by the
repository owner in the **EASY TRAV MASTER SPECIFICATION**. Until that specification and
its reference images have been provided, **make no visual design decisions** — do not
invent a palette, typography, spacing scale, layout language, or motion system, and do
not substitute a generic "modern travel site" look as a placeholder.

## 3. Locked architecture

These decisions are fixed. Do not substitute alternatives, and do not add a library that
duplicates a role already filled below.

### 3.1 Present and preserved

| Concern | Decision |
| --- | --- |
| Framework | Next.js 16, **App Router** only (never the Pages Router) |
| UI runtime | React 19 |
| Language | TypeScript, **strict** |
| Styling | Tailwind CSS v4 (CSS-first config) + custom CSS variables / design tokens |
| Linting | ESLint 9 flat config, `eslint-config-next` |
| VCS | Git |
| Deployment | Vercel — the production build must always stay Vercel-compatible |

### 3.2 Reserved for later — DO NOT INSTALL YET

Introduce each only when the owner asks for the feature that needs it:

| Role | Library | Introduced when |
| --- | --- | --- |
| Advanced animation | **GSAP + ScrollTrigger** | animation work begins |
| Smooth scrolling | **Lenis** — the *only* smooth-scroll controller, and only if genuinely needed | scroll work begins |
| Schema validation | **Zod**, server-side | forms or a backend are introduced |
| Database | **PostgreSQL / Supabase** | persistence is introduced |
| Payments | **Stripe** | payments are introduced |
| Transactional email | **Resend** | email is introduced |
| End-to-end tests | **Playwright**, for critical flows | there are critical flows to protect |

No other animation library, no other scroll library, no CSS-in-JS runtime, no component
kit, no state-management library, no ORM, and no utility grab-bag may be added without
the owner's explicit approval. Prefer the platform, Tailwind, and small local helpers.

## 4. Engineering rules

### 4.1 TypeScript

- `strict` stays on. Never disable it or narrow it for convenience.
- **Never use `any` as an escape hatch.** Use precise types, generics, `unknown` plus a
  narrowing guard, or a discriminated union. If a third-party type is genuinely wrong,
  write a minimal local declaration and comment why.
- Never silence the compiler with `@ts-ignore`, `@ts-expect-error`, or `eslint-disable`
  to get a build green. Fix the root cause. A suppression is acceptable only for a
  documented upstream bug, with a comment naming the cause and the removal condition.
- Type at boundaries: props, route params, server action inputs, API payloads, env vars.

### 4.2 React and Next.js

- **Server Components by default.** Add `"use client"` only where browser interactivity
  genuinely requires it (event handlers, browser APIs, animation, stateful widgets).
- Push `"use client"` to the leaves. Never mark a layout or page client just to let one
  child use a hook.
- Keep data fetching and secret-bearing logic on the server.
- Use App Router conventions: `layout.tsx`, `page.tsx`, `loading.tsx`, `error.tsx`,
  `not-found.tsx`, route handlers, server actions, metadata exports.
- This Next.js version may differ from training data. Before using an API or convention,
  check `node_modules/next/dist/docs/` (see `AGENTS.md`) rather than assuming. Note that
  the scaffold already uses generated global route types such as `LayoutProps<"/">`.
- Use `next/image` for images and `next/font` for fonts. No raw `<img>` for content
  imagery, no `<link>`-loaded webfonts.

### 4.3 Security

- **Never expose server secrets in client code.** Secrets are read only in Server
  Components, server actions, route handlers, or server-only modules.
- **Never put a private key, API secret, service-role key, or webhook secret in a
  `NEXT_PUBLIC_*` variable.** `NEXT_PUBLIC_` means "published to the browser."
- **Never trust client-side validation alone.** Every mutation re-validates its input on
  the server (Zod, once introduced). Client validation is UX only.
- **Never trust prices, totals, currencies, discounts, dates, or availability sent from
  the browser.** Re-derive every money value server-side from authoritative data. The
  client may send identifiers and quantities — never amounts.
- Never trust client-supplied identity, role, or ownership claims; authorise server-side.
- Keep secrets in `.env.local` (git-ignored). Never commit a real secret. Validate
  required env vars at startup rather than reading `process.env` ad hoc.
- Escape or parameterise anything that reaches a database or a shell. No raw string SQL
  interpolation.

### 4.4 Quality baseline — from the first line of product code

- **Accessibility:** semantic HTML, correct heading order, labelled controls, visible
  focus states, keyboard operability, meaningful `alt` text, sufficient contrast, and
  honoured `prefers-reduced-motion` for every animation.
- **Responsive:** design and verify at phone, tablet, and desktop widths. No horizontal
  overflow, no clipped content, no collisions. Recompose at breakpoints rather than only
  shrinking type.
- **SEO foundations:** accurate per-route metadata, one `<h1>` per page, descriptive
  links, canonical URLs, Open Graph, sitemap and robots once routes exist. Never
  keyword-stuff and never promise rankings.
- **Performance:** minimal client JS, correct image `sizes`/`priority`, no layout shift,
  no blocking third-party scripts, lazy-load below the fold.
- **Clean architecture:** clear module boundaries, no duplicated logic, no dead code, no
  commented-out blocks left behind. Colocate by feature; extract shared code only once a
  second real consumer exists.
- **Fix root causes.** Do not hide an error behind a `try/catch`, a fallback value, a
  suppression, or a workaround that leaves the defect in place.

### 4.5 Styling

- Tailwind v4 utilities plus custom CSS variables / design tokens defined in CSS.
- Tokens are the single source of truth for colour, type, spacing, and motion. No
  hard-coded hex values, magic pixel numbers, or one-off gradients scattered in markup.
- The actual token values come from the EASY TRAV MASTER SPECIFICATION. Until then the
  scaffold's placeholder tokens in `app/globals.css` stay exactly as they are.

### 4.6 Definition of done

Before reporting any task complete:

1. `npx tsc --noEmit` passes with no errors.
2. `npm run lint` passes with no errors and no new suppressions.
3. `npm run build` succeeds and stays Vercel-compatible.
4. The change was actually verified, not assumed. Report failures honestly, with output.

## 5. Working agreement

- Do the task asked. Do not widen scope, and do not pre-build features that have not
  been specified.
- **Wait for the EASY TRAV MASTER SPECIFICATION and its reference images before building
  the site.** Until it arrives: no new routes, components, animations, database code,
  authentication, booking functionality, or APIs; no homepage rewrite; no new
  dependencies; no visual design decisions.
- When the specification arrives, treat it as the source of truth for content, layout,
  identity, and behaviour, and record its locked decisions in this file.
- If a request conflicts with a rule here, say so in a sentence or two before acting.
- Ask before anything hard to reverse: force-pushing, rewriting history, deleting files,
  adding a remote, deploying, or touching production data.
- Commit and push only when asked. Keep commits scoped and messages factual.
